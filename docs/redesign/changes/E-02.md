## 1 · Why

- The new theme already points at these handles: `templates/index.json` (category tiles `bracelets`, `necklaces`), `templates/page.our-story.json` and `templates/page.why-brass.json` (`jewelry`). The menus planned in E-04 (`04` §3) link to `/collections/jewelry`, `/collections/bracelets` and `/collections/necklaces`.
- D-08: jewelry lives in its own smart collection driven by the `jewelry` tag, so legacy items can never leak into the jewelry catalogue, even before they are unpublished. Menus link there, not to `/collections/all`.
- D-12: rings stay hidden until ring sizing, stock and exchanges are ready, so **no `rings` collection is created**.
- Created empty and hidden now, so E-04 menus and E-05 Draft products can be checked against real collections in the unpublished preview, without anything reaching customers.

### 1.1 · Deliberate tightening of `04` §3

`04` §3 defines `bracelets` as "type = Bracelet" and `necklaces` as "type = Necklace". This change adds a second condition to each: **and tag = `jewelry`** (all conditions must match). Reason, in the spirit of D-08: a product type alone is free text that any product can carry, so a legacy or merch product given the type `Bracelet` or `Necklace` (by an app, an import or by hand) would appear in a jewelry category. With the tag condition, a product only reaches a category collection when it is also in `jewelry`, so every category is a subset of the jewelry catalogue. It costs nothing: every launch product gets the `jewelry` tag anyway (`phase-3-brief.md` §3.1 step 5, `product-data/`). The `04` §3 table rows for `bracelets` and `necklaces` are updated to match.

## 3 · The exact change

Three `collectionCreate` calls. No description, image, SEO fields, metafields or template suffix (the default `collection` template); nothing published.

| # | Handle | Title | Sort order | Source title | Conditions (all must match) |
| --- | --- | --- | --- | --- | --- |
| 1 | `jewelry` | Jewelry | `CREATED_DESC` | Jewelry tag | product tag is `jewelry` |
| 2 | `bracelets` | Bracelets | `CREATED_DESC` | Bracelet type and jewelry tag | product type equals `Bracelet` **and** product tag is `jewelry` |
| 3 | `necklaces` | Necklaces | `CREATED_DESC` | Necklace type and jewelry tag | product type equals `Necklace` **and** product tag is `jewelry` |

Not created: `rings` (D-12).

Mutation used for each row (values passed as variables):

```graphql
mutation E02Create($collection: CollectionCreateInput!) {
  collectionCreate(collection: $collection) {
    collection { id handle title sortOrder templateSuffix descriptionHtml }
    userErrors { field message }
  }
}
```

```json
{ "collection": {
    "title": "Bracelets", "handle": "bracelets", "sortOrder": "CREATED_DESC",
    "sources": [ { "source": {
      "title": "Bracelet type and jewelry tag", "targetType": "PRODUCTS",
      "inclusion": { "matchType": "ALL", "conditions": [
        { "productType": { "relation": "EQUALS", "matchType": "ANY", "values": ["Bracelet"] } },
        { "productTag":  { "relation": "TAGGED_WITH", "matchType": "ALL", "values": ["jewelry"] } }
      ] } } } ] } }
```

`jewelry` has only the `productTag` condition; `necklaces` uses `"Necklace"`. The product-type condition takes `matchType: ANY` because the API requires it with `EQUALS` (a product has one type, so with a single value it means the same as ALL). The two conditions are joined by `inclusion.matchType: ALL`, so both must match.

Not changed: no existing collection, product, menu, page, redirect or publication; no product joins or leaves any collection.

## 4 · Rollback

The change is additive and the collections are empty and unpublished. Rolling it back means **deleting** them, so under D-28 **tell the owner before doing it**.

1. Read the three collections: `collectionByIdentifier(identifier: { handle: "<handle>" })`, selecting `id productsCount { count } resourcePublicationsV2(first: 10, onlyPublished: false) { nodes { publication { id } isPublished } }`.
2. If one is published anywhere, first unpublish it with `publishableUnpublish(id: <collection id>, input: [{ publicationId: <publication id> }])`. If one has products, note which; deleting a smart collection doesn't change the products themselves.
3. If menus (E-04) or theme settings already link to a handle, repoint or remove those links first, or the links will 404.
4. Delete with `collectionDelete(input: { id: <collection id> })`, using the IDs in §5.
5. Re-read `collectionsCount` and the handles and confirm the store matches [`collections.json`](../backup/2026-11-27/catalog/collections.json) again (14 collections).

A softer rollback that keeps the records: leave them unpublished (they already are). The theme needs no rollback: an unpublished or missing collection reads empty in Liquid, and the category tiles and `pb-featured` collection mode render nothing (D-12, `phase-2-brief.md`).
